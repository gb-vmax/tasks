# Bug Report

### Describe the bug

After importing an OpenAPI 3 spec, I'm seeing duplicate `Accept` headers being generated in the imported requests. When an endpoint has both an explicit Accept header parameter defined in the spec AND response content types, the importer creates two Accept headers instead of keeping just one.

### Reproduction

Given an OpenAPI 3 spec like this:

```yaml
paths:
  /api/users:
    get:
      parameters:
        - name: Accept
          in: header
          schema:
            type: string
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
```

After importing this spec, the generated request contains duplicate Accept headers - one from the parameter definition and another auto-generated from the response content types.

### Expected behavior

The importer should deduplicate headers and only include one Accept header. If an Accept header is already explicitly defined in the parameters, it should take precedence over any auto-generated one from response content types.

### Additional context

This seems to affect any header that might be both explicitly defined as a parameter and auto-generated by the importer. The deduplication logic should handle case-insensitive header name matching since HTTP headers are case-insensitive.
